# P26–P28：图片引用、保存冲突与推送重试

参考 macOS `main` 的 `6abd42a`，在 Linux 当前工作区补充三个独立流程。三路实施分别负责图片模块、冲突审阅组件、Git 重试模块；主线程负责 App、IPC 合同、命令注册和最终验收，另设只读 Git 关键路径复核。

## P26：当前文章的单个图片引用修复

从图片工作台扫描库存并“检查引用与 Alt”，在当前编辑缓冲对应的可靠内联 Markdown 图片条目上选择“修复此引用”。选择库存图片后，界面展示原始目标与将写入的实际编码路径；确认时重新读取并验证图片 SHA-256、MIME 和大小，仅替换该位置的目标字符串。

文章全文、文稿身份、仓库会话、图片清单和所选图片变化均使旧预览失效。Alt、标题、自定义 Front Matter 和其他相同目标保持原样；更改只进入编辑缓冲，之后另行保存。路径继续使用已有站点资源映射，支持中文、空格和括号编码。

只读报告不等于磁盘不存在判断。修复限定当前文章的可靠内联语法；含引用块、列表代码容器、HTML/模板或异常 Front Matter 的文稿保守禁用修复，BOM/YAML/TOML 元数据内不产生修复位置。引用式、HTML、模板、嵌套代码等不支持的语法不会被猜测改写。跨文章磁盘修复、封面/附件模型、资源移动、压缩、裁剪及撤销事务不在本批范围。

## P27：保存冲突审阅

保存返回 `save_conflict` 后，主工作区保留编辑缓冲并提供“审阅保存冲突”。审阅窗口完整展示上次加载、本地未保存和磁盘当前三份纯文本，用户手动编辑合并稿。每份与合并稿均限制为 256 KiB UTF-8；超限或读取失败明确拒绝，不以空文件或截断文本替代。

“备份原稿并载入合并稿”需要明确确认。主线程先复验磁盘，再使用已有 `save_general_draft` 的新建分支持久保存本地原稿并读回核对，最后再次核验磁盘，才以新的磁盘基线把合并稿载入编辑缓冲区。此时没有写回仓库；后续普通保存仍检查该磁盘基线，继续拒绝覆盖外部修改。备份失败、备份内容不一致、磁盘再次变化或文稿上下文失效均不载入合并稿；已经创建的备份保留在通用草稿中。

审阅期间背景编辑与全局快捷键受保护，读取/备份期间不允许切换仓库或文稿。修改过的合并草案重新读取前需确认丢弃。该流程不是自动三方合并，也不替代跨重启恢复档案、安全退出或整个工作区备份；磁盘读取与普通保存沿用已有 RepositoryStore 文件访问边界。

## P28：已提交内容的推送重试

发布中心显式“检查可重试提交”，生成与普通 Commit/Fetch/Push 分离的一次性重试计划。仅支持当前分支的已提交内容；要求暂存区和工作树干净、实时远端同名分支已存在且为本地 HEAD 的祖先。不会自动提交、fetch、rebase 或强制推送。

重试计划审阅冻结 HEAD、远端 SHA、提交数和完整有界历史变更路径；中间提交中新增后删除的文件与合并提交独有路径也纳入。祖先、提交数和路径审阅读取与推送相同的隔离对象视图；原仓库替换引用不能隐藏实际推送内容，原工作树检查不满足时拒绝计划。网络读取、推送和最终核验均使用同一个经过校验的唯一推送 URL；多推送地址、URL 重写和不兼容镜像配置被拒绝。网络 Git 在一次性受控 bare 目录运行，仅借用原仓库对象库，不读取原仓库可变的 transport 配置，避免审阅后的配置重写改变实际目标。HTTP 自动重定向禁用；若远端地址迁移，需要更新配置并重新审阅。计划绑定仓库与 Git 元数据目录身份、分支、HEAD、index/worktree 和远端状态；确认执行前先检查本地身份与目标地址，再联系远端。推送使用冻结 SHA 的单一 refspec，并禁用自动携带标签。

只有重新读取远端且精确等于冻结 SHA 才显示已确认。推送尝试后的失败或网络结果不明要求重新检查远端，不把 Git 进程返回成功当作远端证据。计划最多保留五分钟且只使用一次。此机制不是跨重启发布事务、发布台账、完整 Git 同步或抵抗同账户持续恶意配置竞争的原子事务。
